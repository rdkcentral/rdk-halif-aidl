# meta-rdk-halif

A **reference** Yocto layer for the RDK HAL AIDL interface libraries, generated
from the released snapshots and exercised by this repo's CI (`test.sh` Test 12).
Every released snapshot under `<component>/<version>/` is available as
`rdk-halif-<component>` at version `<version>`, built from its self-contained
CMakeLists — the committed, pre-generated C++, with **no AIDL toolchain or
Python** on the build host.

The integration team owns its production recipes. This layer is here to (a) prove
the per-component build contract works end to end and (b) give you something to
**use as-is or copy and adapt** — see `docs/standards/build_integration.md` for
the contract your own recipes must honour.

## Use (or copy)

Add the layer to `BBLAYERS`:

```bitbake
BBLAYERS += "${TOPDIR}/../rdk-halif-aidl/tests/yocto/meta-rdk-halif"
```

Install the components you need; inter-component dependencies are pulled in
automatically:

```bitbake
IMAGE_INSTALL:append = " rdk-halif-hdmicec"    # brings in rdk-halif-common
```

The Binder SDK is provided by the `linux-binder` recipe (from `linux_binder_idl`);
every HAL recipe `DEPENDS` on it. Pin `SRCREV` to the released tag's commit in
`classes/rdk-halif-module.bbclass` for reproducible builds.

## Version selection, roles and destinations

One recipe per component; `HALIF_VERSION` defaults to the latest snapshot and a
build configuration selects a version per component with
`HALIF_VERSION:pn-rdk-halif-<comp>`. The class also exposes `HALIF_ROLE`
(`vendor` | `mw`) and the install destinations `HALIF_LIBDIR` / `HALIF_INCDIR`.
The sibling **`meta-vendor`** and **`meta-mw`** example layers pin divergent
cohorts (0.2.x vs 0.1.x) via `versions_<team>.yaml` + `scripts/gen_team_conf.py`,
from the *same* recipes.

## Layout

| Path | Purpose |
| ---- | ------- |
| `conf/layer.conf` | Layer definition |
| `classes/rdk-halif-module.bbclass` | Shared build: per-component CMake, lib + header staging, role/dest knobs |
| `recipes-halif/rdk-halif-<comp>/rdk-halif-<comp>.bb` | Generated recipe, one per component (version selected in) |

## Generated — do not hand-edit recipes

The recipes are generated by `scripts/gen_recipes.py`. A recipe's `DEPENDS`
comes from the exact sibling libraries the snapshot links (its resolved
dependency graph), not a hand-written list. Regenerate after adding or bumping a
snapshot:

```bash
./scripts/gen_recipes.py            # regenerate
./scripts/gen_recipes.py --check    # CI guard: fail if recipes are stale
```

The build contract these recipes implement is exercised offline, without
BitBake, by `tests/yocto/run-yocto-per-component.sh` (per-component staging) and
`tests/yocto/run-yocto-roles.sh` (vendor/MW version divergence).

See `docs/standards/build_integration.md` for the full integration contract.
